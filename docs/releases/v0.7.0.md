# v0.7.0 — Release Governance and Trust

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## What changed

### Release identity

- `src/pe_sim/_version.py` is now the single in-code source of `__version__`;
  `pe-sim --version` reads it instead of a hard-coded literal.
- `pyproject.toml` declares `version = "0.7.0"` and declares the project
  license so that the built artifact carries it in its metadata.
- `scripts/release_record.py check-identity` fails when the `pyproject.toml`
  version, `pe_sim.__version__`, and `docs/releases/v<version>.md` disagree, or
  when `src/pe_sim/cli.py` regains a hard-coded version string.

### Distribution inventory

- New `scripts/distribution_inventory.py` produces
  `pe-sim.distribution-inventory.v1`: sorted wheel members with SHA-256,
  declared `Requires-Dist` entries, declared extras, project license
  declaration, and explicit `not_verified` entries for every dependency
  license. Standard library only; no network; no dependency resolution.

### Release record and approval

- New `scripts/release_record.py` with `create`, `approve`, `verify`, and
  `check-identity`.
- A record binds one version, one commit, one tag name, the wheel and sdist
  hashes, the distribution inventory hash, the local gate evidence hash, the
  formal-demo evidence hash, the scope and toolchain policy hashes, and the
  verified toolchain.
- The inventory's recorded wheel hash must equal the supplied wheel hash, so
  gate evidence now points at one exact distribution file.
- `create` always emits `approval.status = "pending"` and
  `signature.status = "not_signed"`. `approve` refuses to run in CI.
- `verify` recomputes every hash and exits non-zero on failure or on a check it
  could not perform.

### CI

- New `release-artifacts` job (Ubuntu, Python 3.12) builds the wheel and sdist,
  writes the distribution inventory and a `SHA256SUMS.txt`, and uploads them as
  a workflow artifact with a 30-day retention.
- The job does not approve, tag, publish, or create a GitHub release.

### Fixes carried into this version

- Detached-HEAD worktree analysis reports `clean` with `branch = "detached"`
  instead of `unknown`, so a detached release checkout can produce formal
  evidence. This fix was committed after the `0.6.1` version bump and ships
  here.
- The formal-comparison rejection test no longer depends on the developer
  worktree being dirty.

## Evidence required before tagging

Ordered, per `docs/27_minimum_local_release_scope_v0.md` and
`docs/53_release_governance_v1.md`:

1. clean commit;
2. `scripts/generate_formal_demos.py` with the exact toolchain;
3. `scripts/release_check.ps1` with `-FormalDemoRunsRoot`, producing
   `release-evidence.json`;
4. `python -m build`, then `scripts/distribution_inventory.py`;
5. `scripts/release_record.py create`, then human `approve`;
6. `scripts/release_record.py verify --require-approved --require-tag`, then
   `git tag -a v0.7.0`.

Steps 4–6 are tooling introduced in this release; steps 1–3 are unchanged.

## Non-claims

- No simulation, physical, thermal, switching, hardware, or engineering claim is
  added. The Stage 12 evidence ladder and the `docs/51` claim conclusion are
  unchanged.
- No artifact or tag is signed. `signature.status` is `not_signed`.
- No PyPI, conda, or container publication.
- No claim that two builds of this source produce byte-identical wheels.
- The distribution inventory is not claimed to conform to CycloneDX or SPDX, and
  dependency licenses are recorded as `not_verified`.

## Tag history note

Git tags exist for `v0.1.0`, `v0.2.0`, and `v0.2.1` only. Versions `0.3.0`
through `0.6.1` were released as source states without tags. This note records
that gap; no tags are back-filled, because a retroactive tag would assert a
review that was never recorded.
