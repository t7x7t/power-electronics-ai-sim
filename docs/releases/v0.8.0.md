# v0.8.0 — Parameter View and Confirmation Record

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## What changed

### Read-only parameter view

- New `pe-sim parameter-view <run> [--compact]` returns
  `pe-sim.parameter-view.v1`: the recorded parameter set of one published,
  integrity-verified package, grouped as `plant`, `controller`, `timebase`,
  `action_policy`, and one `solver:<backend>` group per recorded backend.
- Every value is read from `manifest.json`. The reader does not import a Plant,
  re-execute a model, or re-derive a physical quantity.
- Units, sources, and review status are reported only where a recorded
  applicability finding names the parameter; otherwise they are `null` with
  `provenance_source: "not_recorded"`. No unit is inferred from a field name.
- `parameter_set.digest` is a SHA-256 over the group/component/parameter
  identifiers, values, and units plus the declared bounds, so one digest
  identifies one recorded parameter set.
- The `pe-sim.claim.v1` payload is embedded verbatim from the same code path as
  `inspect-run`, so "what are the numbers" and "what may I claim" cannot drift.

### Parameter confirmation record

- New `pe-sim confirm-parameters <run> --reviewer <name> --statement <text>
  --output <path>` writes `pe-sim.parameter-confirmation.v1` **outside** the run
  package. The record embeds the reviewed parameter rows, the parameter-set
  digest, the package identity, the reviewer statement, the acknowledged
  limitations, and the claim conclusion that was on screen.
- The command refuses to run when `CI` is set, when the reviewer or statement is
  missing, when the output path resolves inside the run package, or when the
  package fails integrity verification.
- New `pe-sim verify-parameter-confirmation <run> --confirmation <path>` returns
  `pe-sim.parameter-confirmation-verification.v1` with status `current`,
  `stale`, `mismatched_run`, `invalid`, or `unknown`. For `stale` it lists the
  changed, added, or removed parameters by name — the confirmation embeds the
  rows precisely so that a later reader does not have to guess.

### Read-only service

- `GET /v1/runs/<run_id>/parameters` serves the parameter view for a verified,
  published package. The service stays GET-only, loopback, and read-only.
- `GET /v1/discovery` gains `inspection_schemas` with the parameter-view and
  claim schema tags. The three visualization contracts and `contract_schemas`
  are unchanged; the parameter view is an inspection surface, not a fourth
  visualization contract.

## Non-claims

- No parameter range is declared for a plant parameter in this release, so
  `range` is `null` and `bounds` contains only declared action-policy limits. A
  future manifest may record ranges and full parameter provenance (open
  decisions PV-1/PV-2 in `docs/54`).
- A confirmation is not an approval of a result, a release, or a downstream use.
  It does not change `evidence_level`, `qualification_level`, or the claim
  conclusion.
- A confirmation is not signed and not tamper-proof. Its value is that it binds
  one reviewer's statement to one parameter-set digest and one package identity.
- `stale` does not block `inspect-run` or `compare-runs`; it is reported only.
- No physical, thermal, safety, or hardware claim is added.
