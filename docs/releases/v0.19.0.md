# v0.19.0 — Agent-Facing Specification Surface

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## What changed in this release

### 1. `describe` / `validate` and structured `issues`

Two read-only subcommands were added, and `run` now refuses a malformed document
with pointer-addressed records instead of one flattened string:

- `pe-sim describe <plant_id>` prints `pe-sim.plant-parameters.v1`: the type,
  unit, bound, default, and description of every `plant_config` field, plus the
  same declaration rendered as a closed JSON Schema (with `x-unit`). An unknown
  id returns the existing `unknown_plant` rejection code.
- `pe-sim validate <config> [--schema PATH] [--backend NAME]` prints
  `pe-sim.spec-validation.v1`: `ok`, `error_count`, `warning_count`, `issues`,
  and `checked`. It exits 2 when any error is present and 0 otherwise. It builds
  no plant, instantiates and calls no adapter, starts no solver, probes no
  backend executable, creates no run directory, and needs no ngspice install.
- When the document is malformed, `pe-sim run` adds two optional fields to its
  `CONFIG_REJECTED` / `invalid_request` envelope: `validation` (= 
  `pe-sim.spec-validation.v1`) and `issues` (an array of `SpecIssue`). **No
  rejection code was added**; `REQUEST_REJECTION_CODES` is unchanged.

`SpecIssue` carries `code`, a JSON Pointer `path`, `message`, `expected`,
`suggestion`, and `severity`. The vocabulary is a closed set of seven codes;
`exploratory_contract_default` is a warning and does not affect `ok`. `checked`
lists the stages that actually ran, so "clean" and "not examined" stay
distinguishable. The full contract is in
`docs/63_agent_facing_spec_validation_v1.md`.

### 2. Declared parameter table for the built-in plants

`src/pe_sim/plant_parameters.py` is new and stdlib-only: `ParameterSpec`,
`PLANT_PARAMETERS` (all eleven built-in plants), `parameter_schema()`, and
`describe_plant()`, under the `pe-sim.plant-parameters.v1` tag. Agreement with
the factories is enforced by `tests/test_plant_parameters.py`: a factory change
that leaves the declaration behind fails the suite.

### 3. `PlantRegistration.parameter_schema`

`PlantRegistration` gained a `parameter_schema` field (`compare=False`,
`hash=False`). Registration validates that it is `type: object`, declares
`additionalProperties: false`, and carries a `properties` mapping; when
`config_keys` is also declared, the two key sets must be identical.
`plant_catalog()` publishes it per plant entry; the top-level keys of the
catalog are unchanged.

### 4. ngspice registrations declare `config_keys`

`ngspice-buck` and `ngspice-sync-buck` moved from `config_keys=None` to an
explicit frozenset. This moves a whitelist the factories already enforced to
validation time; it adds no restriction, because the same whitelist still
rejects unknown keys at build time.

### 5. Validation fallback for third-party plants

A plant registered through the `pe_sim.plants` entry point is resolved through
the registry and is no longer misreported as `unknown_plant`. A plugin that
declares `parameter_schema` gets the same key and value checks as a built-in
plant; an undeclared plugin keeps the shared-schema shape check, and unknown
keys are still rejected by the factory. What is imported is a **declaration**,
not an executable netlist.

### Boundary statement

This release adds surfaces only:

- it **changes no solving behaviour**;
- it **changes no evidence-level derivation** (`time_model.py` is untouched);
- it **changes no review fingerprint** (`reviewed_identities.json` is untouched
  and no pin was added);
- it adds no rejection code and changes the meaning of none;
- the catalog top-level keys, the experiment schema, and the manifest format are
  unchanged.

## Capability ceilings

This release changes no evidence ceiling. The S0–S9 ceiling table in
`docs/releases/v0.18.0.md` still applies (`docs/61` §2.3 / `docs/62` §5). The new
surface produces no new limitation code: `describe` and `validate` are document
checks, and they take no part in route declarations, produce no run evidence,
and raise no ceiling.

A passing `validate` is not a release permission and not a physical or safety
conclusion; it only means the currently declared checks found nothing.

## Baseline

- Version: **0.19.0**. `src/pe_sim/_version.py` and `pyproject.toml` agree and
  `pe-sim --version` prints `0.19.0`.
- Source baseline: commit `95b1eae` (`Close S10 with v0.18.0 release notes and
  artifact parity guard`), which is also `origin/main`.
- Working tree: these changes are **uncommitted** on top of that commit. This
  note does not claim they are committed or tagged.
- Tests (local venv, no ngspice): **1795 passed / 12 skipped** (1807 collected).
  The ngspice matrix was not re-run for this change and is not quoted here.
- Release gate, release record, human approval, and tag: **not produced for this
  version**. The 0.18.0 gate evidence and release record were invalidated by
  these changes because their `source_input_digests` no longer match.

## Not done

- **Step B**: the two-way `TopologyDescriptor` contract, `CircuitPlant`, and a
  generic `ModelBuilder` are not implemented; `describe` covers `plant_config`,
  not circuit structure.
- **Step C**: no SPICE-subset importer; `validate` cannot read a netlist and
  check parameters against it.
- **Cross-field constraints**: relations such as `output_min < output_max` and
  `integration_step_s <= switching_period / 20` are still checked only in the
  model layer. A document can be legal field by field and still be rejected at
  run time.
- The quality of a third-party plant's declaration is the plugin author's
  responsibility; `validate` executes the declaration and does not judge it.
- The 0.18.0 gate / release record / approval / tag remain incomplete, and the
  evidence produced for it is now stale.

## Non-claims

- This note is not approval, not a tag, and not a human sign-off.
- A passing `validate` is not a release permission; `ok: true` only means the
  declared checks found nothing.
- `ParameterSpec` and `parameter_schema` are parameter declarations, not safety,
  qualification, or physical-correctness judgements, and they do not replace
  human review.
- `severity=warning` does not affect `ok` and does not block a run.
- No rejection code was added, and document checking is not described as a
  security boundary.
