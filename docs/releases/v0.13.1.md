# v0.13.1 — Reconstruct the Remaining On-Time When a Segment Starts Mid-Pulse

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## Why this release exists

An independent verification of 0.13.0 found a real defect in the phase
parameterisation. The 0.13.0 netlist shifted the **next rising edge** correctly,
but a segment that starts while the carrier is inside an on-pulse also needs the
**rest of that pulse**. Without it, the segment delivered less energy than the
duty asked for, and every observation still looked plausible.

The failure was not a corner case:

| Probe | 0.13.0 result |
| --- | --- |
| `control_period = 1.2 × Tsw`, 8 windows vs one direct run | output 10.82% low |
| 0.01% load change at 2.5 µs (inside the 4 µs on-pulse) | output 18.61% low, run still `QUALIFIED` |
| Same change at 7.5 µs (off-phase) | 8.5e-6 relative — correct |

The 1.5-period acceptance test never saw it because its window boundaries fall at
phases 0 and 5 µs, both outside the 4 µs on-pulse.

## Changed

### 1. A finite tail pulse for a mid-on segment

When `0 < phase < duty*Tsw`, the template now renders:

```text
Vpwm  pwm_pulse 0 PULSE(0 1 {TD} 1e-9 1e-9 <pulse_width> {Tsw})
Vtail pwm_tail  0 PWL(0 1 <duty*Tsw - phase> 1 <... + 1e-9> 0)
Bpwm  pwm       0 V = V(pwm_pulse) + V(pwm_tail)
```

The linear behavioural source sums the periodic carrier with the remaining
on-time. A segment that starts at a phase at or after the falling edge gets no
tail and keeps the 0.13.0 netlist shape. The switch still sees a 0/1 V control
signal with 1 ns edges, so the device model and solver settings are unchanged.

### 2. Two counterexample tests, now part of the acceptance

- `test_a_window_boundary_inside_the_on_pulse_keeps_the_energy`: `1.2 × Tsw`,
  eight windows vs one direct run, 1% output / 2% current tolerance.
- `test_a_change_inside_the_on_pulse_is_applied_at_its_declared_time`: a 0.01%
  load change at 2.5 µs must not move the final state by more than 1%. This test
  fails by 18.6% without the tail.

The netlist unit test also asserts the tail and the summing source for a segment
starting at phase 3 µs of a 4 µs pulse.

### 3. Two documentation corrections from the same verification

- `_solve_window`'s comment and the release note used to say "never past the
  window end". That is true for the Runner, which never requests past the window
  end, but a direct API caller may request a longer duration. The code now says
  what it does: solve to the window end **or** the requested duration, whichever
  is longer; a change point forces a re-solve because the inputs no longer match.
- The review note said the deleted restriction was an `uncheckable_rules` entry.
  It was a hard `NumericalLimit` (`control_period.min_switching_periods`). The
  model claim's `limitations` no longer claims that integer ratios are required.

`applicability.py`'s `control_period.min_switching_periods` check is kept: it is
claim-driven, so a third-party plant that declares that limit still gets the
check. The built-in `ngspice-buck` no longer declares it, so the check never
fires for it.

### 4. Review pin updated

`implementation_sha256` is now
`1af1fcdbd1b311410639e5328b03275b22f5bf3a586a7880519f875c3e347a2e`, with the
tail reconstruction and both counterexample tests named in the review note.

## Not changed

- Duty remains zero-order-hold within a solve segment; the controller still runs
  once per control window.
- Comparator-level events remain out of scope for this route (`docs/60` D3 stays
  open with B3).
- No public API name changed; `pe_sim.__all__` is untouched.
