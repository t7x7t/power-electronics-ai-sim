# v0.9.2 — Identity Verification Boundary

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## Why this release exists

v0.9.1 tightened the adapter location check from a file base name to resolved
paths. An independent follow-up found that the resolved path is still read from
`cls.__module__`, which is a plain writable attribute that `inspect.getfile()`
merely trusts. A class defined anywhere could name `pe_sim.reference_plants`,
inherit the reviewed `manifest_identity()`, and report `verification: verified`.

Reproduced before this release: a subclass defined in
`.tmp/forge_p01b/reference_plants.py`, named `BuckPlant`, with `_rk4_step()`
setting `vout = 123.456` and `__module__ = "pe_sim.reference_plants"`, produced
`status = verified`, `module_path = reference_plants.py`, and a `QUALIFIED` run.
`Runner` accepted it because the class name also matched its registration.

## Fixed

### 1. A class name is not a location (`identity.py`)

`verify_adapter_identity()` now requires three independent conditions before it
reports `verified`, and reports `module_outside_solve_path` with a distinguishing
reason when any of them fails:

1. the resolved defining file is a declared solve-path file (unchanged from
   0.9.1);
2. the declared module really binds this class object under its declared
   qualified name — resolved through `sys.modules`, not through the attribute
   the class writes about itself;
3. every function-like attribute the class defines itself was compiled from a
   declared file, which also rejects a foreign class rebound into a reviewed
   module's namespace and a reviewed class whose methods were replaced at
   runtime.

The verdict gains `class_bound_in_declared_module`, `class_code_files`, and
`class_code_outside_solve_path`. All three stay portable: declared relative
paths and attribute names, never absolute paths. The status vocabulary is
unchanged, so `CONTRADICTED_VERIFICATION_STATUSES`, `credibility`, and the
formal-comparison gate keep working as before.

## Not fixed, and why

Two adjacent cases are outside the boundary on purpose, and the reasoning is now
part of the documentation rather than a gap:

- **instance attributes are not judged.** The caller supplies the object, so
  rebinding `plant.step` after construction is the caller's own act, equivalent
  to passing a different object.
- **callables without a code object are not judged.** A C extension has no
  source file to compare, and guessing at one is worse than saying so.

`docs/38_kernel_review_v0.md` §2.1 records the full non-goal list and why the
third question — "where did this arbitrary object's code come from?" — has no
answer in CPython. `docs/03_agent_operating_policy_v0.md` §8 adds the triage
rule: a finding is fixed only when it names a non-malicious failure mode, so
further adversarial reports are answered by that list instead of another check.

## Behaviour changes

- A subclass of a reviewed plant that used to verify by claiming the reviewed
  module now reports `module_outside_solve_path` and is capped below
  `comparable`. This is the intended behaviour: a subclass is not the reviewed
  class object.
- Verified shipped plants are unaffected. The manifest gains keys inside
  `plant.verification` only; `manifest_sha256` is recomputed per run, and
  `schemas/manifest.schema.json` already allows additional properties there.

## Verification

- `tests/test_adapter_verification.py`: 19 passed, including four new
  regressions — forged `__module__`, an alias subclass with no own code, a
  foreign class rebound into the reviewed namespace, and a tampered run that is
  capped below `comparable`.
- Full suite: 1086 passed, 7 skipped.
