# v0.20.0 — Circuit Topology Authoring Surface

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## What changed in this release

### 1. A closed device vocabulary (`pe-sim.circuit-devices.v1`)

`src/pe_sim/circuit_devices.py` is new and stdlib-only. It declares the eight
component kinds a topology may use, each with its ordered ports, the net kinds
each port may bind, and the parameters it renders:

| kind | SPICE letter | ports (in card order) |
| --- | --- | --- |
| `voltage_source` | `V` | positive, negative |
| `pulse_source` | `V` | positive, negative |
| `inductor` | `L` | input, output |
| `capacitor` | `C` | positive, negative |
| `resistor_load` | `R` | positive, negative |
| `voltage_controlled_switch` | `S` | input, output, control |
| `freewheeling_diode` | `D` | anode, cathode |
| `averaged_switch` | **none** | input, output, control |

The vocabulary is a *device* vocabulary, not a topology vocabulary: nothing in
the module names a converter, which keeps `docs/43` invariant I5 intact.
Parameters reuse `ParameterSpec` from `pe_sim.plant_parameters`, so a circuit
parameter and a `plant_config` field are described by one shape.

`averaged_switch` is the one kind with no element card. It exists because the
project ships averaged reference models that declare it; a compiler must refuse
it rather than invent a circuit that was never reviewed.

**Optionality rule:** a parameter with a default may be omitted; every other
parameter must be supplied. The compiler never substitutes a value for a
parameter that has no default.

### 2. Structural validation (`pe-sim.topology-validation.v1`)

`src/pe_sim/topology_validation.py` is new and stdlib-only. It turns the
one-way descriptor export into a checkable document contract:

- 26 closed issue codes (22 errors, 4 warnings);
- JSON-Pointer paths, `expected`, and safe `suggestion` fields on every issue;
- connectivity, reference-net, control-net, and ideal-voltage-source-loop
  checks that the descriptor constructor never performed;
- a `checked` list naming only the groups that actually ran;
- `fingerprint` is **optional** for an authored document, with the computed
  digest returned in the envelope. Making an agent implement SHA-256 over
  canonical JSON would be a trap, not a gate.

The validator distinguishes a **valid descriptor** from a **compilable
circuit**. A descriptor containing a behavioural block is the former and is
reported as a `not_compilable` *warning*, so the project's own averaged
references are not flagged as broken.

### 3. Deterministic netlist compilation (`circuit-netlist-v1`)

`src/pe_sim/circuit_compile.py` is new and stdlib-only. It renders a descriptor
into one ngspice netlist:

- element cards follow descriptor order, values use one fixed format, and
  nothing time-, host-, or path-dependent is written, so the SHA-256 of the text
  is a stable identity for the compiled circuit;
- 13 closed refusal codes;
- exactly one actuator and exactly one carrier are required, because the kernel
  commands one dimensionless duty ratio; the pulse width is derived from the
  `duty` argument rather than read from the descriptor.

The compiler's correctness is established by comparison, not by assertion.
`tests/test_circuit_compile.py` holds the compiled circuit to the project's
reviewed Buck template two ways: the `(letter, nodes)` sequence of every element
card must be identical, and - when `PE_SIM_NGSPICE` is set - both netlists are
solved by the same ngspice and their operating points compared. Measured on
2026-10-29 at D = 0.5, Vin = 12 V, L = 100 µH, C = 470 µF, R = 10 Ω,
fsw = 100 kHz over a 20 ms window:

```text
compiled  vout=6.022243  iL=0.638947
reviewed  vout=6.022284  iL=0.638935
delta     vout=4.077e-05  iL=1.190e-05
```

### 4. Three read-only CLI commands

| command | purpose |
| --- | --- |
| `pe-sim describe-devices [kind]` | print the device vocabulary, or one kind |
| `pe-sim validate-topology <file>` | print `pe-sim.topology-validation.v1` |
| `pe-sim compile-topology <file> [--duty D] [--duration S] [--step S] [--integrator trap\|gear\|euler] [--output P] [--json]` | render and print or write a netlist |

All three are dispatched **before** `load_builtin_plants()`: a circuit question
needs no plant registration and no solver. They build no plant, instantiate and
call no adapter, start no solver, probe no backend executable, and create no run
directory.

### Boundary statement

This release adds surfaces only:

- it **changes no solving behaviour**;
- it **changes no evidence-level derivation** (`time_model.py` is untouched);
- it **changes no review fingerprint** (`reviewed_identities.json` is untouched
  and no pin was added);
- **no rejection code was added**; `REQUEST_REJECTION_CODES` is unchanged. A
  compile refusal travels as `invalid_request` with `compile_code` and
  `details` in the envelope;
- `pe_sim.__all__` and `tests/fixtures/public_api.json` are unchanged: the new
  modules are reachable but carry no compatibility promise yet, exactly like the
  Step A surface;
- the catalog top-level keys, the experiment schema, and the manifest format are
  unchanged.

One message changed shape: `describe` no longer wraps its unknown-plant message
in the repr quoting `str(KeyError)` adds. The envelope fields and codes are
identical.

## Capability ceilings

This release changes no evidence ceiling. The S0–S9 ceiling table in
`docs/releases/v0.18.0.md` still applies (`docs/61` §2.3 / `docs/62` §5). The new
surface produces no new limitation code: it is a document authoring path, takes
no part in route declarations, and produces no run evidence.

A topology an agent authors has no review record. Whatever is eventually
executed from one can therefore reach at most `limited` evidence - never
`comparable` - under `docs/22`.

A passing `validate-topology` is not a correctness proof and not a release
permission. A successful compile is not a reviewed model.

## Baseline

- Version: **0.20.0**. `src/pe_sim/_version.py` and `pyproject.toml` agree and
  `pe-sim --version` prints `0.20.0`.
- Source baseline: commit `296fba1` (`Tighten the agent surface after scenario
  testing`), which is also `origin/main`.
- Working tree: these changes are **uncommitted** on top of that commit. This
  note does not claim they are committed or tagged.
- Tests (local venv): see the commit message for this release; the ngspice
  matrix was run locally with `PE_SIM_NGSPICE` set and is quoted in
  `tests/test_circuit_compile.py`'s acceptance test.
- Release gate, release record, human approval, and tag: **not produced for this
  version**. The 0.18.0 gate evidence and release record remain invalidated
  because their `source_input_digests` no longer match; v0.19.0 never had one
  either.

## Not done

- **`CircuitPlant`**: there is no execution adapter driven by a descriptor.
  `NgspiceBuckPlant` still renders through the reviewed Buck template.
- **Generic `ModelBuilder`**: not decoupled from `BuckNetlistParameters`.
- **Carrier phase**: the reviewed Buck template supports starting a solve
  segment mid-carrier and rendering the remaining on-time as an extra pulse.
  The generic compiler writes a phase-0 carrier only, so it cannot yet replace
  the reviewed template in a zero-order-hold segmented run.
- **Complementary control**: a descriptor that declares two gate nets (the
  synchronous, model-controlled, and peak-current references) is a valid
  descriptor but is refused at compile time. Declaring how several control nets
  derive from one duty scalar is the next increment.
- **Step C**: no SPICE-subset importer.
- **Cross-field constraints**: relations such as `output_min < output_max` and
  `integration_step_s <= switching_period / 20` are still checked only in the
  model layer.
- The 0.18.0 gate / release record / approval / tag remain incomplete, and the
  evidence produced for it is stale.

## Non-claims

- A descriptor is not electrical truth, and a compiled netlist is not a
  validated model.
- The device vocabulary is finite: eight kinds, three net kinds. There is no
  mutual inductance, transformer, controlled source, non-linear device,
  subcircuit, or `.include`.
- No thermal, device, reliability, or hardware behaviour is modelled.
- Nothing here is a safety conclusion.
