# v0.9.5 — Unknown Is a Legal Status, Reserved Names Are Base Names

**Status:** release note. This note describes what changed. It is not approval,
not a tag, and not a claim about any simulation result.

## Why this release exists

0.9.4 fixed a real defect and introduced one of its own in the same function.
An independent follow-up caught it. It is recorded here as a regression, not as
a new finding.

## Fixed

### 1. DEFECT-3: an explicit `status: "unknown"` became `declaration_invalid`

0.9.4 stopped letting an unregistered status token fall through to inference, so
`"trusted"` became `declaration_invalid` (correct). The allow-list it introduced
was `{"declared", "partial"}`, which also excluded `"unknown"` — a token the
class itself accepts.

Because `normalise_parameter_provenance` returns a `ParameterProvenance` object
unchanged, the same declaration meant two different things depending on the
container:

| Adapter returns | 0.9.4 result |
| --- | --- |
| `{"status": "unknown", "records": [...]}` | `declaration_invalid` — `unsupported parameter provenance status: 'unknown'` |
| `ParameterProvenance(status="unknown", ...)` | `unknown` |

Downstream this moved the finding from `parameter_provenance_unknown` to
`parameter_provenance_invalid`. The misclassification was conservative — it
could not raise an evidence level — but it is exactly the read-side
inconsistency `docs/57` §2 says will be fixed.

`unknown` is now a legal token in both forms. The records and an optional
`declaration_error` are preserved, an empty record list still resolves to
`unknown`, and an unregistered token such as `"trusted"` is still invalid. A
parametrised test now asserts mapping/object parity for `declared`, `partial`,
and `unknown`, so the two forms cannot diverge again.

### 2. Reserved device names are base names, not whole strings

`validate_run_id`'s comment said reserved names apply "with or without an
extension", but the check compared the whole string, so `COM1.txt`, `NUL.txt`
and `con.log` were accepted. Windows treats the base name before the first dot
as the device name.

This was reported as a portability observation rather than a defect, because the
write path and the attestation path agreed. It is fixed anyway: the comment
already declared the rule, and an id that only works on some Windows
configuration is a reproducibility problem, not a style issue. Both sides reject
it now, since the attestation side delegates to the same function.

## Not changed

- No new module, no new public API name; `pe_sim.__all__` is untouched.
- The `partial` inference for an explicit `None` value and the
  `declaration_invalid` result for unregistered tokens are unchanged.
- Nothing in `docs/57` §3 was defended.

## Verification

- `tests/test_parameter_provenance_validation.py`: 21 passed, including the
  parity test that fails on 0.9.4 for all three legal tokens.
- `tests/test_run_id_consistency.py`: 18 passed; `COM1.txt`, `NUL.txt` and
  `con.log` are rejected by both the write and the attestation side.
- Reported failing assertion reproduced on 0.9.4:
  `assert 'declaration_invalid' == 'unknown'`.
- Full suite: 1130 passed, 7 skipped.
