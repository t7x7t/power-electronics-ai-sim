# v0 约束保证架构说明：机器约束、人工审查与证据留痕

## 文档状态

本文是面向使用者、维护者和审查者的**设计说明草案**，用于解释当前项目为何采用“机器强制约束 + 人工边界审查 + 证据留痕”的组合架构，以及一次仿真如何在该架构下运行。

本文不是安全认证、硬件设计批准或研究结论。文中关于流程、责任和未来能力的内容需要项目负责人进行人工核验。当前 v0 仅实现了其中一部分公共契约、最小 Runner、基础安全/资格检查和运行产物记录，不能据此宣称真实 PSFB、硬件安全或产品就绪。

## 1. 为什么需要三部分组合

电力电子仿真同时面对三类不同风险：

1. **可机械判定的运行风险**：例如字段缺失、时间回退、动作越界、非有限数值、产物缺失或 Hash 不匹配。
2. **必须结合工程语境的边界风险**：例如模型是否足以代表目标电路、参数是否符合额定条件、实验是否能支持某个研究问题。
3. **事后无法仅凭记忆恢复的证据风险**：例如运行使用了哪个提交、哪个模型、哪个输入、哪个规则版本，以及失败时发生了什么。

单独使用任一方式都不够：

- 只靠机器检查，容易把“格式正确”误认为“工程上合理”；
- 只靠人工检查，容易漏掉重复出现的时间、接口和产物错误，也难以稳定复核；
- 只保存结果图或最终数字，无法证明数据来源、失败路径和处理过程。

因此三部分的分工是：

```text
机器约束   -> 及时阻止可判定的违规行为
人工审查   -> 判断模型、目的和结论是否越过工程边界
证据留痕   -> 让运行事实、判断依据和限制可追溯、可复核
```

这不是给使用者增加形式流程，而是把“运行是否成功”“数据是否可用”和“结论能说到哪里”明确拆开，避免一次看似成功的仿真被过度解释。

## 2. 三部分各自负责什么

### 2.1 机器强制约束

机器约束适用于可以给出确定答案的规则。典型规则包括：

- 实验配置和 Manifest 必须通过 JSON Schema；
- 时间戳必须单调，且满足 `sample_time <= action_time <= next_advance_end`；
- Controller 只能获得获准的 measurement，不能接收 Plant truth；
- 动作必须有限并处于声明的边界内；
- Plant、Controller 和运行契约的来源必须有独立标识或 Hash；
- 输出先写入临时目录，必需产物齐全后才能原子发布；
- 失败运行不能被覆盖为成功运行；
- 不支持的 capability、契约不匹配或缺失来源信息不能静默补全。

机器检查失败时，系统应拒绝启动、停止当前动作，或将运行标记为 `RUN_FAILED`、`INCOMPLETE`、`DISQUALIFIED` 等明确状态。指标较好不能覆盖安全失败或证据缺失。

### 2.2 人工边界审查

人工审查适用于无法仅凭结构和数值判定的工程问题，例如：

- Plant 是否代表本次研究对象，而不是只代表一个方便运行的替代物；
- 初始状态、负载范围和安全阈值是否有合理来源；
- 当前证据是否足以支持 `mechanism`、`functional` 或更高等级的表述；
- 结果是否被误读为器件额定、硬件实时性或产品安全结论；
- 是否允许把某个运行作为正式基线、比较对象或学习输入；
- 第三方模型、数据和文献是否可以使用或发布。

人工审查不是事后给成功运行“盖章”，而是在高风险边界处作出显式决定，并记录审查者、依据、限制和时间。没有人工批准时，系统可以保留探索性运行，但不得自动升级其证据等级或进入正式基线/可选学习流程。学习/自适应属于下游可插拔扩展，不是核心基础设施的必选交付物。

### 2.3 证据留痕

每次运行都应保留足以回答以下问题的证据：

- 使用了什么配置、代码、模型、环境和契约？
- Runner 实际执行了哪些采样、动作、输入和状态转换？
- 是否发生过安全、资格、能力或运行错误？
- 输出文件是否完整，是否可由 Hash 校验？
- 结论、比较或学习准入基于哪些原始产物？
- 哪些边界仍未验证，谁作出了人工决定？

在当前 v0 中，运行目录包含 `manifest.json`、`config.snapshot.json`、`environment.json`、`qualification.json`、`safety.json`、`metrics.json`、`events.json`、`samples.npz` 和日志目录。此结构用于承载事实和限制；它本身不保证模型物理正确。

## 3. 约束如何变成可执行检查

每条约束应从原则转换为可审计的检查定义：

```text
约束 ID
  -> 可观察条件
  -> 检查时机
  -> 检查器
  -> 失败状态/动作
  -> 证据产物
  -> 责任人和规则版本
```

例如，“Controller 不得读取 Plant truth”可以展开为：

| 项目 | 定义 |
|---|---|
| 可观察条件 | Controller 调用参数只包含 measurement 白名单，不包含 truth 对象或隐藏状态 |
| 检查时机 | 接口构造、Controller 调用和负向测试 |
| 失败动作 | 拒绝调用并记录契约错误 |
| 证据 | 接口定义、测试结果、事件和 Manifest 引用 |
| 责任 | 基础设施维护者实现；验收者独立复核 |

建议将约束分为五组：

1. **结构约束**：Schema、类型、枚举、必需字段和禁止字段。
2. **时间/因果约束**：时间单调、采样年龄、动作延迟、预览输入可见窗口和调用次数。
3. **接口/权限约束**：measurement 白名单、Plant truth 隔离、capability 协商和只读边界。
4. **生命周期约束**：状态机合法转移、失败不可伪装、学习前置条件和人工审批状态。
5. **来源/产物约束**：提交、工作树状态、环境、配置/模型/契约 Hash 和原子发布完整性。

机器约束的目标是“fail-closed”：无法确认满足规则时，不继续产生可能被误用的正式结果。它不应通过自动填默认值、删除失败日志或修改状态字符串来制造成功表象。

## 4. 人工边界如何落地

人工审查应采用结构化审查记录，而不是只在聊天或口头会议中确认。每条边界至少记录：

```text
boundary_id
问题和预期答案
所需证据
审查者
决定（通过/退回/限制/待补证据）
审查时间
适用范围和限制
```

以下变更应默认停下来请求人工确认：

- Plant 参数、初始状态、安全阈值或基线 profile；
- Controller 可见字段、时间因果或执行边界；
- 公共契约、Schema、状态机或证据等级；
- 未知来源模型、第三方资料或发布内容；
- 将结果解释为器件、硬件、实时性、产品或安全结论；
- 将运行提升为正式基线、可比较结果或学习输入。

推荐由实现者和验收者分离：实现者提供代码、测试和运行产物；验收者检查需求覆盖、失败路径、越权风险、证据完整性和结论限制。验收不能只重复成功测试，还应包含非法输入、未来数据、能力缺失、状态非法跳转、产物不完整和来源未知等场景。

## 5. 一次仿真的用户体验

用户不需要手工执行每个内部检查，但应能理解以下流程：

1. **准备实验**：选择 Plant、Controller、输入 schedule、时间基准、初始状态和资格规则；系统读取 Schema 和已有契约。
2. **运行前检查**：系统检查配置、来源、Hash、capability、输出目录和必要审批。缺失信息会拒绝启动或标记为探索性/未完成。
3. **运行中约束**：Runner 按固定顺序采样、调用 Controller、执行安全检查、推进 Plant、记录事件。时间回退、未来信息、非有限值和动作越界会停止后续动作。
4. **运行后整理**：系统保存样本、事件、指标、检查结果、环境和 Manifest，并原子发布运行目录。失败也保留失败证据。
5. **资格与边界审查**：机器先判断数据是否可用，再由用户或指定工程师确认模型适用范围、比较条件和结论等级。
6. **可视化/报告**：未来的图表和报告应引用 `run_id` 及其原始产物，不应脱离 Manifest 单独传播。图表只能展示已批准的证据范围。
7. **基线或学习准入**：只有满足资格、可比性、来源和人工审批条件的运行，才允许进入正式基线或学习流程。

对用户而言，收益不是“每次都得到一个绿色成功标记”，而是能够区分：运行是否完成、数据是否有效、实验是否合格、结果是否可比较，以及结论是否得到足够支持。

## 6. 适用场景与不解决的问题

### 适用场景

- 多个 Plant、Controller 或实验由同一 Runner 反复运行；
- 需要比较不同控制器、输入 schedule 或模型版本；
- AI Agent 参与代码、测试、仿真和数据整理；
- 运行失败、环境变化和结果来源需要事后复核；
- 研究结果需要明确适用范围，避免被误读为硬件结论。

### 不解决的问题

该架构不能自动证明：

- 电路模型的物理真实性或参数合理性；
- 器件额定值、热设计、EMI、可靠性或硬件实时性；
- 某个控制算法具有普遍最优性或研究价值；
- 仿真结果可以直接替代台架、器件、硬件在环或认证测试；
- 第三方资料具有发布许可；
- 人工审查者的判断本身一定正确。

系统可以限制越权结论、要求补证据并保留不确定性，但不能代替领域工程师承担这些判断。

## 7. 当前 v0 的真实完成度

当前已经具备：

- `ExperimentSpec`、`PlantObservation`、`ActionRequest` 等公共数据契约；
- Fake Plant/Fake Controller 和最小闭环 Runner；
- 时间单调、未来动作、非有限动作等基础 fail-closed 检查；
- 基础资格检查、安全记录、状态和事件记录；
- 临时目录、原子发布、Manifest 和 SHA-256 产物索引；
- Experiment/Manifest JSON Schema 和 Gate 1/2 测试。

当前尚未具备或尚未核验：

- 真实 `D:\PySpice`/PySpice/Ngspice PSFB Plant 迁移；
- 完整 Git dirty 基线拒绝、人工审批凭据和边界审查记录格式；
- 完整多速率/事件时序、能力协商和状态机审计；
- 通用指标、可视化、报告及其到原始运行的追溯链；
- 自动化的比较、学习准入和证据等级升级流程；
- 跨环境真实模型的确定性和物理有效性证明。

因此当前实现只能证明公共运行骨架和部分约束机制可工作，不能把 fake backend 结果解释为真实 PSFB 或硬件结论。

## 8. 待人工核验事项

项目负责人在进入后续实现前，应确认：

1. 正式需求拥有者、最终批准者和各类边界的责任人是谁；
2. 哪些约束属于强制拒绝，哪些约束允许探索性运行但必须降级证据；
3. 人工审查表、审批记录和结论限制的正式字段与保存位置；
4. `RUN_OK`、`QUALIFIED`、`COMPARABLE` 的批准条件；若启用可选学习/适配扩展，再明确 `LEARNING_ELIGIBLE` 的批准条件；
5. 真实 PySpice/Ngspice 迁移、可视化和报告阶段的验收门槛；
6. 谁可以批准安全阈值、模型适用范围和基线；若启用可选学习/适配扩展，再明确学习输入的批准人。

在这些事项明确前，任何缺失的边界信息都应保持为 `INCOMPLETE` 或探索性状态，而不是默认通过。
